# 2026-09-15

## 新建 sysmon —— OKX 持仓/策略的「任务管理器」伪装 TUI

**需求**：用 Go 写一个 TUI，查看合约与策略，但要伪装成电脑监控软件；
可配置 OKX key，可配置显示内容（用户举例：BTC 显示成 `cpu`、ETH 显示成 `cpu2`）。

**确认过的设计选择**（问过用户）：
- 界面风格 → Windows 任务管理器（不是 htop）
- 数值映射 → 全面伪装（盈亏率当 CPU%、保证金当内存，数值看起来完全是系统指标）
- 数据源 → 持仓 + 全部策略

**产出**：`F:/projects/RJDJ/sysmon/`（独立 go module，零第三方依赖，`sysmon.exe` 已编译）

结构：
- `internal/config` — JSON 配置，**支持 `//` 与 `/* */` 注释**（自写 stripJSONComments）
- `internal/okx` — 从 `backend/internal/okx` 抽取的只读精简客户端（签名逻辑一致，补了模拟盘 header）
- `internal/feed` — 拉持仓/策略(tradingBot 五类)/行情，按配置映射表组装成统一 Row
- `internal/fake` — 伪装映射引擎：业务数值 → 监控指标 + 平滑正弦抖动
- `internal/tui` — Windows 控制台 API（syscall.NewLazyDLL）+ 自研双缓冲画布 + 三页签

**映射规则**：CPU←|收益率|×100、内存←保证金×0.2、磁盘←|浮盈|×0.02、
网络←|24h涨跌|×100×0.3、GPU←杠杆/20×100、电源←按 CPU% 分级。每条映射可用 `*_scale` 调。

**关键实现点**：
- 终端 raw mode / 尺寸 / 光标 / WriteConsoleW 全部走 kernel32（`syscall.NewLazyDLL`），无 x/term 依赖
- 抖动用多段正弦叠加而非随机数，数字连续漂移才像真实负载
- 重绘 250ms、取数 refresh_ms（默认 3s），引擎内部按 refresh 节流记录历史与趋势
- 画布需自行处理 CJK 宽字符（runeWidth），宽字符右半格用 R=0 占位
- 列宽公式：`nameW = w - fixed - ncol - 2`（每列尾部 1 列间隔 + 左 1 列边距），
  算错会把最右列挤出画布
- `-dump WxH` 参数可把三个页签渲染成纯文本，非交互环境下预览外观/做回归
- `-check` 参数打印映射对照表，配 key 前先确认

**踩坑**：Edit 工具在本环境偶发「报成功但未落盘」，多次编译失败都是这个原因；
后续每次改完关键处立刻 grep 校验。

**待办**：用户尚未填真实 API Key，未在真实账户上验证过 tradingBot 各接口的返回。

## sysmon 第二轮：盈亏方向可见（用户反馈）

**用户反馈**：看不出哪个是正的哪个是负的；并复述了映射关系
（CPU%=收益率、内存=保证金、磁盘=浮动盈亏、网络=24h涨跌幅、GPU%=杠杆倍数）。

**根因**：映射引擎对五个指标统一取了 `math.Abs()`——负的 CPU 占用/负内存会立刻穿帮，
但副作用是盈亏方向被吃掉了。

**方案**：方向不放进指标值，改由独立字段承载。
- `fake.Proc` 新增 `Dir int`（+1 盈 / -1 亏 / 0 中性），由 `dirOf()` 判定：
  先看 `UplRatio`，为 0 时退回 `Upl`；`Row.Err != ""` 直接返回 0。
- 进程页签新增「趋势」列（宽 4），置于名称之后：红 `+` / 绿 `-`，装饰进程留空。
- **刻意用 ASCII 的 `+ -` 而不是 ▲▼ ↑↓**：那些是 Unicode Ambiguous 宽度字符，
  中文终端常按两列渲染，会让整表列错位。
- CPU 列颜色保持 `loadColor`（负载语义）不动，避免整屏红绿破坏伪装。
- 新增 `D` 键按方向排序。
- `gpu_scale` 从硬编码 `/20*100` 提成可配项（默认 5，设 1 即与杠杆 1:1）。
- 缩放系数取值改用 `orDef()`：配置未经 normalize 时系数为 0 会让整列指标静默归零。

**列索引整体后移一位**（名称0 趋势1 PID2 状态3 CPU4 内存5 磁盘6 网络7 GPU8），
`sortCol` 默认值、`toggleSort` 按键映射、`sortProcs` 的 switch 三处必须同步改。
另导出 `config.Config.Normalize()` 供测试直接构造配置。

**新增测试** `internal/fake/engine_test.go`：方向穿透、装饰进程无方向、
盈亏同幅时 CPU 相等、gpu_scale 生效。

## sysmon 第三轮：真实账户暴露的 OKX 策略接口 bug（必修）

用户已在 `sysmon/config.json` 填入**实盘** Key，跑 `-check` 后暴露三个策略接口全挂：

| 类别 | 报错 | 根因 |
| --- | --- | --- |
| grid | `50014 Parameter algoOrdType can not be empty` | 首个轮询值传了空串 |
| signal | `50014` → 改后 `51000 Parameter algoOrdType error` | 取值错，**不是 `signal` 而是 `contract`** |
| algo（条件单） | `51000 Parameter ordType error` | 该端点要 `ordType`，代码却传 `algoOrdType` |

**修法**（`internal/okx/data.go`）：把「子类型参数」从写死的 `algoOrdType` 提升为
`botPath{param, values}` 配置，各类自己声明：

- grid → `algoOrdType` = `grid` / `contract_grid`
- dca → `algoOrdType` = `spot_dca` / `contract_dca`（原样）
- recurring → `algoOrdType` = `recurring`（原样）
- signal → `algoOrdType` = **`contract`**（合约信号）
- algo → **`ordType`** = `conditional` / `oco` / `trigger` / `move_order_stop`

删掉 `algoOrdTypesFor()`。`GetStrategies` 里按 `bp.param` 决定补 `AlgoOrdType` 还是 `OrdType`。
`BotStrategy` 补 `OrdType` / `FloatPnl` / `FrozenBal` 字段，feed 的取值链相应加长
（upl: Upl→TotalPnl→FloatPnl→FloatProfit；margin: InvestAmt→FrozenBal→Margin→QuoteSz）。
`labelOf` 对条件单按 ordType 细分（双向止盈止损/单向触发/移动止盈止损）。

**结果**：5 类策略全部拉通，警告归零，条目 9→11。

**教训**：信号策略是独立模块（文档目录叫「信号交易」），虽然 REST 路径仍在
`/api/v5/tradingBot/signal/` 下，但参数语义与网格不同，不能想当然。

## sysmon 第四轮：进程页加「实时价格」两个伪装列

**用户问**：性能页看的是什么？可以查看实时的价格。

**先查清了现状**：行情**早就在拉**（`GetTickers`），`Row.MarkPx/AvgPx/Chg24h` 都有值，
但 `tui/app.go` 里 `MarkPx`/`AvgPx` **一处都没被引用**——价格拉回来存进结构体后被丢掉了。
`Chg24h` 只喂给「网络」列；`MarkPx` 完全没用上。

**用户选的方案**（给过选项）：进程页加伪装列 / 保持 3 秒轮询（不做 WebSocket）。

**选列过程（重要，别再重走）**：要找一个「任务管理器本来就有、取值区间又够宽」的列来装价格。
- 线程数 → 量级不对：BTC 63,385 无论乘多少都不像真实线程数（真实上限几百）
- 句柄数 → 量级合适（15~10,000）但小价格标的会被压到 1，不可信
- **提交大小 / 页面错误** → 最终选它俩：都是任务管理器「详细信息」页的真实列名，
  区间分别是 几 MB~几十 GB、几百~几百万，价格放进去不用额外伪装；且两者物理量不同，
  数字接近也不会被交叉验算

**默认系数定为 0.1（不是 1）**：一开始用 1:1，跑出来 BTC 的「提交大小」是 **61.9 GB**，
而配置里 `mem_total_gb` 写的是 16——一台 16 GB 内存的机器上出现 61.9 GB 的进程太扎眼。
改成 0.1 后 BTC 落在 6,339 MB，正常范围。**读法统一成「该列数字 × 10 = 价格」**。
`price_scale` / `avg_scale` 可按条目覆盖；价格极小的标的（LAB 0.05）要设 1000。

**格式化的坑**：`fmtCommit` 刻意**固定用 MB、不自动升到 GB**。
升到 GB 后 BTC 那行变成 6.2 GB，反算回价格还要再乘 1024，把读法搞乱了。
导出成 `tui.FmtCommit` / `tui.FmtFaults` 供 `-check` 复用，避免两处规则各写一遍走偏
（第一版就踩了：自检里写 `%.0f MB`，0.1 MB 显示成 "0 MB"）。

**两列不加抖动**：引擎其余指标都叠正弦抖动，但这两列存在的意义就是数字准，抖了就偏了。

**顺带修的**：`GetTickers` 原来只拉 `instType=SWAP`，现货网格/现货定投标的取不到价；
改成并发合并 SWAP + SPOT 两份行情。

**踩坑（本环境反复出现）**：Edit 工具在**同一条消息里并行改同一个文件**时，
后一次写入会以陈旧内容为准、把前一次覆盖掉（报 success 但没落盘）。
本轮 config.go / engine.go / app.go 各中招一次。**同一文件的多处修改必须一条一发，改完立刻 grep 校验。**

## sysmon 第五轮：五个监控指标改成 1:1（用户要求去掉所有倍率）

**用户反馈**：「现在的计算太复杂了」，点名 内存×0.2 / 磁盘×0.02 / 网络×0.3 / GPU×5
「都不要乘以倍率，直接加上单位就行」。

**改动**：
- `config.go` 五个系数默认值全部 1（CpuScale 本来就是 1）；`engine.go` 里
  `projectRow` 的兜底默认值同步改成 1.0。系数字段保留，仅作「想整体放大/缩小某列」的调节。
- **上/下限要放宽**：原来 `baseDisk`/`baseNet` 封顶 99.9，1:1 后会把不同盈亏压成同一个数。
  磁盘与网络改封顶 999.9（SSD 几百 MB/s、千兆网卡几百 Mbps 都正常）；
  CPU/GPU 仍是百分比，封顶 100 不变。
- **`mem_total_gb` 默认 16 → 32**：内存列 1:1 等于保证金，演示数据保证金合计 14.4 GB，
  在 16 GB 机器上占比 90% 反而扎眼；改 32 后落在 44.5%。规则：≥ 总保证金 ÷ 1024。
- 价格两列**维持 0.1 不动**（用户没点名；1:1 会让 BTC 现价显示成 61.9 GB 的提交大小）。
- 同步：`config.example.json`、用户的 `config.json` 注释块、README 映射表与预览快照、main.go 头部注释。
- 新增测试：`TestDefaultScalesAreOneToOne`（fake）、`TestIndicatorScalesDefaultToOne`（config）、
  `TestScaleOverride`（系数仍可覆盖）。

**实盘核对**：账户总权益 10,253 USD，保证金合计仅 1.2 GB → 16 GB 机器上内存占比 7~9%，正常；
表单里 BTC-cpu 显示 内存 1102.5 MB，对应保证金 1103 U，1:1 成立。
